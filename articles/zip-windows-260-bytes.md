ブラウザの中で複数のファイルに日本語の名前を付け、ZIP にして渡すツールを作っています。その過程で、「名前が長いファイルが 1 つ混ざるだけで、Windows のエクスプローラーが ZIP 全体を開けなくなる」という仕様を知り、名前を切る処理を文字数からバイト数に直しました。

先に結論を書きます。

- Windows のエクスプローラーは、ZIP の中の名前が UTF-8 で 260 バイト以上のファイルが 1 つでもあると、ZIP 全体を「圧縮 (zip 形式) フォルダーは無効です」として開けません（日本マイクロソフトの Windows サポートチームのブログによる）。
- 数えるのは文字数ではなくバイト数です。日本語は UTF-8 で 1 文字 3 バイトなので、日本語だけの名前なら約 86 文字で届きます。
- ZIP 自体は壊れていません。PowerShell の `Expand-Archive` や 7-Zip では展開できます。
- ブラウザ側で名前を作るなら、`String.length` ではなく `TextEncoder` でバイト数を数えて、文字の境目で切ります。

## 何が起きるか

出典は日本マイクロソフトの Windows サポートチームのブログ記事「エクスプローラーで ZIP ファイルを展開すると『圧縮 (zip 形式) フォルダーは無効です』エラーが発生する」（2026-06-24）です。

https://jpwinsup.github.io/blog/2026/06/23/Shell/Explorer/zipfldr-maxpath-japanese-encoding/

記事によると、エクスプローラーの ZIP の展開は、中の各ファイルの名前のバイト数を調べ、260 以上のものが 1 つでもあれば ZIP 全体をエラーにします。対象は ZIP の中に記録された名前だけで、展開先のフォルダーの場所や、長いパスを許す設定（LongPathsEnabled）は関係しません。影響を受けるのは Windows 11 の全バージョンと Windows Server 2016 以降と書かれています。

ここで気づきにくいのが、単位がバイトだという点です。`String.length` で 120 文字までに収めていても、日本語だけなら 360 バイトになります。たとえば取引先名が長い請求書の名前（日付・取引先・金額・書類番号をつなげたもの）や、元のファイル名を残す設定で元の名前が日本語で長い場合に届きます。利用者から見ると「ZIP が開けない」としか見えず、原因は 1 件だけの長い名前です。

## 直し方

名前（拡張子を除く）に、文字数の上限とバイト数の上限の両方を掛けます。バイト数は `TextEncoder` で数えます。

```ts
const MAX_STEM_LENGTH = 120;
// 拡張子と重複の連番（_2 など）を足しても 255 バイトに収まるようにする
const MAX_STEM_BYTES = 240;

const encoder = new TextEncoder();
const utf8Length = (s: string): number => encoder.encode(s).length;

/** 文字数と UTF-8 のバイト数の両方の上限に収まるよう、文字の境目で末尾を切る */
function fit(s: string, maxLength: number, maxBytes: number): string {
  let out = "";
  let bytes = 0;
  for (const ch of s) {
    const n = utf8Length(ch);
    if (out.length + ch.length > maxLength || bytes + n > maxBytes) break;
    out += ch;
    bytes += n;
  }
  return out;
}
```

要点は 2 つです。

- `for (const ch of s)` はサロゲートペア（𠮷 のような 4 バイトの文字）を 1 文字として扱うので、文字の途中で切って壊すことがありません。`s.slice(0, n)` で切ると、サロゲートペアの片方だけが残ることがあります。
- 上限を 259 ではなく 240 にしたのは、拡張子（`.pdf`）と、同じ名前が重なったときの連番（`_2`）を足したあとでも 255 バイトに収めるためです。255 バイトは、多くのファイルシステムが 1 つの名前に許す上限です。

名前の部品が複数あるときは、削る順を決めておきます。このツールでは、検索に使う取引先を残し、元のファイル名から先に削ります。

## 確かめたこと

取引先名を日本語 200 文字にした名前は、直す前が 332 バイト、直したあとが 242 バイト（240 に拡張子と連番の分を足した値）でした。ブラウザで ZIP を作ったあと、中央ディレクトリを読んで名前のバイト数を見ています。

もうひとつ、ZIP の名前に UTF-8 の目印（汎用目的ビットフラグのビット 11）が付いているかも確かめました。付いていないと、Windows は名前を OS の文字コード（日本語環境なら Shift_JIS 系）として読み、文字化けします。fflate のようなライブラリで ZIP を作る場合は、日本語の名前に目印が付くことを自分の ZIP で確かめておくとよいです。

確かめていないこともあります。ここで書いた手元の確認は、ZIP の中の名前のバイト数と目印までです。実際の Windows のエクスプローラーで開けるかは、まだ自分の画面では試していません。「260 バイト以上で開けない」という挙動は、上のマイクロソフトの記事に書かれていることを根拠にしています。

## 余談：Mac は逆の問題がある

同じ ZIP を Mac の標準の解凍（アーカイブユーティリティ）で開くと、名前の濁点・半濁点が「文字と記号に分かれた形（NFD）」で保存されます。ZIP の中の名前が 1 文字にまとまった形（NFC）でも同じでした（macOS 15.7.4 で確認）。ZIP に入れるときは NFC に揃え、名前を比べるテストでは両側を `normalize("NFC")` してから比べるのが安全です。
